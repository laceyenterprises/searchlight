Methodology

How Searchlight tests search

A controlled experiment: the same agent, model and instructions in every run, with only the search setup changing. The steps first; the full apparatus after.

  1. Step 1 of 5

    Give the agent a real job

    A research brief or a code fix about something that changed after the model's training cutoff, or a question with a well-documented answer.

  2. Step 2 of 5

    Change only the search

    The same agent, model and instructions every time. Each run plugs in one search provider at its default settings.

  3. Step 3 of 5

    Run it sealed, three times

    Each run starts in a fresh, isolated workspace, and every task runs three times: 18–42 runs per setup. Every search and page visit is logged.

  4. Step 4 of 5

    Grade it blind

    Automatic checks run where a task has them. Otherwise an AI judge compares the answer with the saved source pages, never told which setup produced it.

  5. Step 5 of 5

    Rank it honestly

    Setups are ranked by how often their runs passed. Every pass rate shows its 95% range.

Terms used in the reports

The reports keep their technical words. Each one, with the plain word this site uses:

Search setup

Report term: arm
One way of giving the agent search: one provider's connector, the agent's built-in search (native), or no search at all.

Test run

Report term: cell
One task, one search setup, one repetition, graded once.

Agent

Report term: harness
The AI coding agent program: Claude Code or Codex.

Benchmark names

Report term: GAP, WSB, SEW
The search gap bench, the web search bakeoff, and the Search Evaluation Workbench that runs them.

Connector

Report term: MCP server
The standard connector that plugs a search provider into an agent.

No search, answer handed over

Report term: floor, ceiling
The same task with no search (floor) and with an excerpt containing the answer handed over (ceiling). A task counts only if the agent fails at the floor and passes at the ceiling.

Gap closed

Report term: gap closure
How far a search setup got from the floor toward the ceiling: 1.00 means all the way.

Grader, agreement

Report term: judge, kappa
An AI model that grades answers without knowing the setup. In the search gap bench a Claude Code judge decides and a Codex judge checks; kappa measures their agreement (1 is perfect, 0 is chance).

Tokens per pass

Report term: tokens per success
Tokens used per passing run; the search gap bench counts failed runs' tokens too.

95% range

Report term: Wilson 95% CI
The range the true pass rate likely falls in, worked out with Wilson's method so it never runs past 0% or 100%.

Chance of a fluke

Report term: p-value (McNemar, Fisher, sign test)
How likely a difference this large would be if the setups were really equal. Below 0.05 is the usual bar for a real difference.

Held-back questions

Report term: holdout
Questions kept back from tuning, so a result cannot be fitted to them.

Fixed in advance

Report term: pre-registered
Questions and scoring rules fixed before any results were seen.

What each setup can touch

Search setups differ only in what the agent can use to search. Claude Code is started with --strict-mcp-config, so the only MCP server it can reach is the provider's, and --tools limits its built-ins. Codex runs read-only with its shell, browser, app and plugin features disabled. After each run an audit compares every observed tool call with the setup's contract; a call outside it marks the run contaminated.

  A[search setup contract] --> CC[Claude Code spawn<br/>--strict-mcp-config<br/>--tools: the setup's built-ins<br/>--allowedTools: the same set]
  A --> CX[codex spawn<br/>exec --sandbox read-only<br/>--disable shell_tool, browser_use,<br/>apps, plugins, ...]
  CC --> P1[search provider:<br/>one provider MCP server<br/>+ ToolSearch + Read]
  CC --> N1[built-in search:<br/>WebSearch + WebFetch + Read]
  CC --> F1[no-search / floor / ceiling:<br/>no tools]
  CX --> P2[search provider:<br/>one provider MCP server]
  CX --> N2[built-in search:<br/>codex --search]
  CX --> F2[no-search / floor / ceiling:<br/>no tools]
  P1 & N1 & F1 & P2 & N2 & F2 --> AU[setup audit:<br/>every observed tool call<br/>checked against the contract]

Which tasks count

A search gap task counts only if it is genuinely beyond the model: with no search the agent must fail, and with the answer excerpt handed over it must succeed. Calibration is repeated for each agent and model.

flowchart LR
  T[candidate brief<br/>event after 2026-01-01] --> FL[floor: no search<br/>5 runs]
  T --> CE[ceiling: answer excerpt<br/>in the prompt, 5 runs]
  FL --> Q{floor passes ≤ 1<br/>and ceiling passes ≥ 4?}
  CE --> Q
  Q -- yes --> AD[admitted for this<br/>agent and model]
  Q -- no --> RJ[rejected]
  AD --> BAT[battery: every search setup x 3]
  BAT --> GC[gap closure =<br/>setup - floor / ceiling - floor]

gap closure  =  (setup pass rate − floor pass rate) / (ceiling pass rate − floor pass rate)

   floor          search setup           ceiling
   0% ●─────────────────●──────────────────● 95%
       └──── closed ────┘└──── remaining ────┘

How answers are graded

sequenceDiagram
  participant A as Agent answer
  participant V as Schema validator
  participant S as Source capture
  participant J1 as Judge 1 (Claude Code)
  participant J2 as Judge 2 (Codex, gap bench)
  A->>V: JSON deliverable (brief, claims, citations)
  V-->>A: reject malformed answers
  A->>S: cited URLs
  S->>J1: readable source text + rubric (blinded to the search setup)
  S->>J2: same inputs
  J1-->>A: key-fact recall, unsupported claims, decision
  J2-->>A: independent labels, agreement recorded
  Note over A,J2: pass = right decision AND recall >= 0.7 AND unsupported <= 0.25

Search gap briefs pass when the decision is right, at least 70% of key facts are covered and at most 25% of claims are unsupported. Code fixes pass when hidden tests pass in an isolated workspace. Bakeoff tasks use automatic checks where a task has one, and otherwise a single blinded grader scores the task rubric.

The search API head-to-head

One study tests the search APIs themselves rather than an agent using them. It sends the same pre-registered research questions to Exa, Tavily, Parallel and Firecrawl, each with the parameters its own documentation recommends, on the same day and with the same number of results. The results are pooled and shuffled, and blind model judges verify every counted claim on its source page. A provider is credited only when its own result page states the claim, and a claim counts as new only if the knowledge base the questions came from did not already have it. Unlike the benchmarks above, each question ran once, so the study reports counts without intervals.

flowchart LR
  Q[pre-registered question sets<br/>from one knowledge base] --> E[Exa] & T[Tavily] & P[Parallel] & F[Firecrawl]
  E & T & P & F --> PO[(results pooled,<br/>deduplicated, shuffled)]
  PO --> J[blind model judges<br/>verify each claim on its page]
  J --> K{already in the<br/>knowledge base?}
  K --> A[attribution rejoined:<br/>credit only where the provider's<br/>own page states the claim]
  A --> R[reports/*/summary.json]

Its sets, endpoints, amendments and costs are in the study's methodology, and its full pre-registered record is in reports/2026-09-26-search-api-head-to-head/.

Insight studies

An insight study sends one fixed set of questions to every search and research service, each run as its vendor documents. A model extracts each answer's claims, another checks every claim on the page it cites, and a blind judge values what each verified finding is worth to the question's reader. A service earns a finding only if its own cited page supports it. Each study page links its full record.

Reproduce, correct, contribute

Install Searchlight, run sew doctor, then follow each study's reproduce.md. Raw transcripts and provider responses are not distributed, so exact replay of the published numbers is not possible; a new run measures the same method. The one exception is the search API head-to-head's Monitors probe, whose raw responses are published. If you run a tested service and a configuration here misrepresents it, open an issue with the configuration you recommend: corrections are rerun and published beside the original, never silently replaced.

New reports appear on this site by themselves: publish a report directory under reports/ (or run sew insight publish), rebuild, and its page, its rows and its index entries are generated from its files.

pipx install 'git+https://github.com/laceyenterprises/searchlight'
sew doctor
python3 scripts/check_reports.py
python3 scripts/build_site.py --check
