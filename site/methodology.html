Methodology

How Searchlight tests search

The same agent, model and instructions in every run; only the search setup changes.

The words used here

  1. Step 1 of 5

    Give the agent a real job

    A research brief or a code fix about something that changed after the model's training cutoff, or a question with a well-documented answer.

  2. Step 2 of 5

    Change only the search

    The same agent, model and instructions every time. Each run plugs in one search provider at its default settings.

  3. Step 3 of 5

    Run it sealed, three times

    Each run starts in a fresh, isolated workspace, and every task runs three times: 18–42 runs per setup. Every search and page visit is logged.

  4. Step 4 of 5

    Grade it blind

    Automatic checks run where a task has them. Otherwise an AI judge compares the answer with the saved source pages, never told which setup produced it.

  5. Step 5 of 5

    Rank it honestly

    Setups are ranked by how often their runs passed. Every pass rate shows its 95% range.

From task to report

One test run = task × search setup × repetition. Every tool call is recorded, and the grader never learns the setup.

What each setup can touch

An audit checks every tool call against the setup's contract; a call outside it marks the run contaminated.

The exact commands

Claude Code

claude --print --output-format stream-json --verbose --no-session-persistence \
  --model claude-opus-5-5 --mcp-config <run>/claude-mcp.json --strict-mcp-config \
  --tools ToolSearch,Read --allowedTools 'mcp__<provider>__*'     # one search provider

  --tools '' --allowedTools ''                                       # no search, floor, ceiling

Which tasks count

A gap task counts only if the agent fails it with no search and passes it with the answer handed over.

How answers are graded

Two judges see the same inputs; neither is told the search setup.

Code fixes and bakeoff tasks

Code fixes pass when hidden tests pass in an isolated workspace. Bakeoff tasks use automatic checks where a task has one, and otherwise a single blinded grader scores the task rubric.

The search API head-to-head

The APIs themselves, with no agent: the same pre-registered questions, each run once, so counts without ranges.

Sets, endpoints and the full record

Each API was set up as its documentation recommends, the same day and with the same number of results. Its sets, endpoints, amendments and costs are in the study's methodology, and its full pre-registered record is in reports/2026-09-26-search-api-head-to-head/.

How an insight study works

One fixed set of questions goes to every search and research service, graded blind on the pages each one cites.

What the study measures

An insight study sends one fixed set of questions to every search and research service, each run as its vendor documents. A model extracts each answer's claims, another checks every claim on the page it cites, and a blind judge values what each verified finding is worth to the question's reader. A service earns a finding only if its own cited page supports it.

Reproduce, correct, contribute

Install Searchlight, run sew doctor, then follow each study's reproduce.md. Raw transcripts and provider responses are not distributed (except the head-to-head's Monitors probe), so a new run measures the same method rather than replaying the numbers. If a configuration here misrepresents a service you run, open an issue: corrections are rerun and published beside the original.

pipx install 'git+https://github.com/laceyenterprises/searchlight'
sew doctor
python3 scripts/check_reports.py
python3 scripts/build_site.py --check
